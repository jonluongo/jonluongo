# Superset — Implementation Plan

Seven requests, ordered so the widest change lands last and nothing collides.

## Already done — no work needed

**"Repeat Workout" should say Continue.** That wording lived in `SessionDetailView`, which was deleted when Today absorbed the session. The button now reads **"Resume Session"** while a session is part-logged and **"Open Session"** once it is finished. The owner is on an older build.

---

### Task 1: The close button is not round and its icon is off-centre

`ActiveWorkoutView`'s toolbar puts the chevron and the elapsed clock in **one `HStack` inside one `ToolbarItem`**. The toolbar draws one background behind the whole item, so the "circle" is really a capsule sized to chevron-plus-spacing-plus-time, and the chevron sits at one end of it rather than in its middle.

Give the chevron its own `ToolbarItem`. Decide where the elapsed time goes — its own item, or the title area, which is where a session's running time reads naturally.

### Task 2: Rest timers — one place to control them, and a way to switch them off

Two requests that are one problem:

> "the rest timer should be togglable for users who dont want it"

> "instead of having the rest timer configurable from the top maybe i can just tap the rest timer on each workout to edit it since theyre all different. Then we can completely move the top one?"

He is right that they are all different: rest is prescribed **per exercise**, and a single control in the toolbar cannot mean anything specific. `Rest 3min` is already drawn at the top of each exercise's card — **make that the control.** Tapping it edits that exercise's rest; it is the only place rest appears, so it is the only place rest should be changed.

Then the toolbar timer button goes, as he suggests.

**The switch-off.** Decide what "off" means and where it lives. Consider: off for this exercise (belongs on the same tap) versus off everywhere (a preference, and the Account page is read-only by his instruction — so it would be the second thing in the Units section, which is the one part of that page that is genuinely his). **Both may be needed; say what you chose and why.**

**Constraint that must hold:** editing rest changes what *runs*, not what Claude *prescribed*. A prescription silently rewritten by a tap in the gym is the bug that was removed in commit `9593820`; do not reintroduce it. If the lifter's chosen rest and the prescribed rest differ, the screen must not claim the plan asked for the lifter's number.

### Task 3: An info popup on an exercise

> "there should be an option on here for an info popup with the name of the workout and a placeholder for the animations we are going to add and maybe a description"

The catalog already holds, per exercise: display name, primary and secondary muscles, equipment, movement pattern, mechanic, difficulty, and `instructions` for about 18% of entries. Exercise identity is the **MoveKit slug**, chosen so purchased animations drop in without a mapping layer — so the placeholder has a real home.

Show what the catalog holds and nothing it does not. An exercise with no instructions shows none rather than a blank heading.

The exercise row already pushes its **history**. Decide how info and history relate — two destinations, or one screen with both — and do not end up with two screens that each show half of an exercise.

### Task 4: Supersets

> "the ai should be able to build supersets into the plan not sure whats required to add this in an organized way"

The deepest change here, and it touches every layer:

- **`PlanDocument`** — exercises are a flat list per day. A superset is a *grouping*: two or more exercises performed back to back, resting only after the group.
- **`write_plan`'s schema** — Claude must be able to express it, and unknown keys are refused by name, so this is an additive format version.
- **`PlanImporter` and the store** — a group has to persist.
- **The logging screen** — the round is the unit, not the set. This is the part with real UI consequences: a superset's rows interleave, and rest runs after the group rather than after each exercise.
- **The snapshot** — Claude must read back what was actually done.

**Judge whether to do it in one task or split format from interface.** Say which and why. The format is useless without the screen, and the screen cannot be built without the format.

### Task 5: Rename Barbell → Superset

> "i want to go through and do a full app rename from Barbell to Superset. I need you to make sure all of the relevant text is renamed correctly."

**Rename:** the display name, every user-facing string, the design vocabulary's `barbell*` font roles, doc comments, `CLAUDE.md`, and the specs and plans where they describe the product rather than record history.

**Do NOT rename**, and say so plainly in the report:

- **The bundle identifier** `com.jonluongo.LiftingPlan` and the iCloud container `iCloud.com.jonluongo.LiftingPlan`. Changing either orphans the container, the snapshot already synced, and the app's data on the owner's phone.
- Historical records — ledgers, execution logs, and commit messages are what happened.

The owner's own `Barbell.icon` is his file and his to rename.

Do this **last**: it touches nearly every file, and doing it earlier would collide with everything above.

## Standards

The app makes no training decisions, invents no values, and asks the lifter nothing about training. Absence stays absence. No gamification. Spacing 4/8/12/16/24, tap targets ≥44pt, Dynamic Type, no colour literals. Layers import downward only. Swift 6, strict concurrency, warnings-as-errors. Files past ~300 lines are a signal. Swift Testing, never XCTest.

**Reuse before building.** A new component needs a reason.

**When in doubt, lighter** — the owner has asked for this in four separate messages now.

# LiftingPlan Data Audit

Scope: `LiftingPlan/Catalog/Resources/exercises.json` (412 entries, generated by
`Tools/build-catalog.py` from `Tools/derivation-rules.json` +
`Tools/overrides.json`), the SwiftData models in `LiftingPlan/Store/`, and the
generator script itself. No code or data was changed.

**Framing note (owner directive, mid-audit):** the catalog is permanently
fixed — "the lego bricks that we build with" — users will never add
exercises. That makes catalog **coverage** a structural, unfixable-by-users
property of the app, and every wrong catalog **entry** a bug the owner alone
can fix, and only by shipping a new build. Both sections below are weighted
accordingly.

---

## 1. Catalog data quality

Spot-checked 65+ entries against domain knowledge (bench/squat/deadlift
family, rows, pulldowns, curls, presses, flyes, hip ab/adduction, shrugs,
carries, plyometrics, olympic lifts, core). Found **13 confirmed-wrong
entries** in that sample, plus two systemic rule defects that likely affect
entries not individually checked. The existing `CatalogIntegrityTests` suite
does **not** catch any of these — its slug-vs-muscle check only tests a fixed
token list (`abduction`, `calf`, `tricep`, `bicep`, `hamstring`, `quad`,
`glute`, `chest`, `shoulder`, `lat`, `trap`, `forearm`, `neck`) and never
checks `pattern`, `equipment`, `mechanic`, or `difficulty` against slug
semantics the way this audit did.

### Critical

**`barbell-spinal-jefferson-curl`, `dumbbell-spinal-jefferson-curl`,
`kettlebell-spinal-jefferson-curl`, `bodyweight-spinal-jefferson-curl`** — a
new instance of the exact substring-collision class this project has been
bitten by before. The Jefferson curl is a loaded spinal-flexion / hamstring
mobility movement (weight held, back rounds vertebra by vertebra). Because
the slug ends in `-curl`, `derivation-rules.json`'s `pattern` table matches
the generic `curl` key and the entry gets `pattern: "curl"`,
`primaryMuscles: ["biceps"]`, `secondaryMuscles: ["forearms"]`. That is wrong
for all four entries — there is no bicep involvement at all. Should be
something like `pattern: "flexion"` or `"stretch"`,
`primaryMuscles: ["hamstrings"]` or `["lower back"]`. **Fix:** add explicit
overrides for the four `*-spinal-jefferson-curl` slugs (`overrides.json`
already has a `nordic-hamstring-curl` precedent for exactly this pattern).

**`kettlebell-turkish-get-up`** — `mechanic: "isolation"`. The Turkish get-up
is one of the canonical full-body compound movements (hip hinge + lunge +
shoulder stability + rotation in one rep); it is used in programming
specifically because it is compound. Tagging it isolation is indefensible.
**Fix:** override `mechanic: "compound"`; also consider widening
`primaryMuscles` beyond `["abdominals"]` alone (shoulders and glutes are
at least as load-bearing).

**`kettlebell-farmers-carry`** — `mechanic: "isolation"`. A loaded carry is a
textbook compound, full-body movement. This is not an isolated slug bug: the
`carry` movement pattern is simply missing from `compoundPatterns` in
`derivation-rules.json`, so every carry-pattern exercise defaults to
isolation unless fedb enrichment or an override corrects it (sled-push
happens to get `compound` from fedb enrichment; farmer's-carry does not).
**Fix:** override `mechanic: "compound"` for farmer's-carry-type entries
specifically — do not blanket-add `carry` to `compoundPatterns`, since
`dead-hang`, `plate-pinch`, and `bird-dog` are legitimately isolation/static
holds and would become wrong the other direction.

### Important

**`barbell-upright-row`, `dumbbell-upright-row`** — both tagged
`pattern: "horizontal pull"`. An upright row moves the bar vertically along
the torso; it is not a horizontal-pull movement in any standard taxonomy
(closer to vertical pull / its own lane). Root cause: neither slug has an
explicit pattern-table entry, so `longest_match` falls through to the
generic `row` substring, which maps to `"horizontal pull"`. Someone already
noticed the primary-muscle fallout of this (both entries carry an override
setting `primaryMuscles: ["shoulders"]`) but never fixed the `pattern`
field, so the catalog now asserts a shoulder-primary exercise with a
horizontal-pull pattern tag — internally inconsistent, and it pollutes
`substitutes(for:)`, which matches on `pattern`: asking for a substitute for
a barbell row will surface upright rows as if they were interchangeable.
**Fix:** add `"pattern": "vertical pull"` (or a new pattern value) to both
overrides.

**`stability-ball-leg-curl`, `towel-slide-leg-curl`** — both tagged
`equipment: "machine"`. Neither uses a machine — a stability-ball leg curl
is a bodyweight/stability-ball movement, a towel-slide leg curl is bodyweight
on a floor. Root cause: the equipment table has an explicit
`"leg-curl": "machine"` rule (correct for `hamstring-curl`, `lying-leg-curl`,
`seated-leg-curl`), and it fires as a substring match on these two slugs
too, clobbering the equipment actually named earlier in the slug. Three
sibling `*-leg-curl` slugs (`band-leg-curl`, `dumbbell-leg-curl`,
`cable-single-leg-laying-leg-curl`) already have overrides fixing exactly
this; these two were missed. **Fix:** add
`"stability-ball-leg-curl": {"equipment": "other"}` and
`"towel-slide-leg-curl": {"equipment": "bodyweight"}` to `overrides.json`.

**`jumping-jack`, `jump-rope`** — both `difficulty: "advanced"`. Jumping
jacks and rope-skipping are beginner-level warm-up/conditioning movements
that appear in essentially every beginner program; tagging them "advanced"
is the kind of error a lifter will notice immediately and lose trust over.
Root cause: `difficultyByPattern` in `derivation-rules.json` blanket-assigns
`"advanced"` to the entire `olympic` and `plyometric` patterns, with no
allowance for movement complexity within the pattern (see §5 — this is a
rule design defect, not a one-off typo, and likely affects other
`plyometric`-pattern entries not individually re-checked here; `burpee` is
a plausible additional offender since it is commonly programmed for
beginners). **Fix:** either give `jumping-jack`/`jump-rope` explicit
overrides, or split `difficultyByPattern` so low-skill plyometrics don't
inherit the Olympic-lift rating.

**`barbell-deadlift`** — `primaryMuscles: ["lower back"]`,
`secondaryMuscles` includes hamstrings/glutes/quads/lats/traps/etc. This is
free-exercise-db's own data (unmodified by any override) and is a
well-known quirk of that dataset: mainstream strength-training
classification treats the deadlift's prime movers as the hip extensors
(glutes, hamstrings), with the erectors/lower back working isometrically as
stabilizers rather than as the defining mover. Getting the primary muscle of
the single most load-bearing lift in the catalog wrong matters more than
almost any other entry — muscle-group filtering (`ExerciseFilter.muscles`
matches on `primaryMuscles` only) means a hamstring- or glute-focused
session generator would not surface the deadlift at all under a strict
primary-muscle filter. **Fix:** override `primaryMuscles: ["hamstrings",
"glutes"]`, move `"lower back"` to secondary.

### Minor

- `tibialis-raise` — `primaryMuscles: ["calves"]`. Tibialis anterior
  (dorsiflexion) is functionally the antagonist of the calf
  (plantarflexion). Correct behavior given the 17-value muscle taxonomy has
  no "shins"/"tibialis" entry — flagging only so the owner knows it's a
  taxonomy gap, not an oversight, if that muscle group is ever added.
- `entry["primaryMuscles"] or ["abdominals"]` fallback in `build-catalog.py`
  (line 135) is dead code today — every pattern in `patternMuscles`
  (including the `carry` default) resolves to a non-empty list, so the
  fallback can never fire under the current rule tables. Not a bug, but
  worth removing or leaving a comment explaining it's defensive-only, so a
  future rule-table edit that removes a `patternMuscles` entry doesn't
  silently start tagging things "abdominals."

**Estimated scope:** 13 confirmed-wrong entries out of 65+ sampled (~20%
hit rate in the sample), plus two systemic rule defects
(`compoundPatterns` missing `carry`; `difficultyByPattern` blanket-rating
plyometrics "advanced") that were not exhaustively re-run against every
matching entry. A full pass filtering on `pattern == "carry" && mechanic ==
"isolation"` and `pattern == "plyometric"` would likely turn up more.

## 2. Catalog coverage

Computed full distributions (`python3` over `exercises.json`, 412 entries).

```
equipment:  bodyweight 90, dumbbell 81, barbell 66, machine 55, cable 53,
            kettlebell 26, band 18, cardio machine 11, plate 3, other 2,
            ez bar 2, sled 2, trap bar 2, medicine ball 1
pattern:    hinge 44, curl 44, horizontal pull 39, horizontal press 36,
            cardio 34, squat 29, raise 27, lunge 25, extension 22,
            vertical pull 20, vertical press 19, olympic 13, fly 13,
            rotation 11, shrug 9, carry 9, flexion 8, plyometric 6, stretch 4
difficulty: beginner 239 (58%), intermediate 153 (37%), advanced 20 (5%)
primaryMuscles: quadriceps 106, glutes 58, shoulders 42, chest 42,
            hamstrings 41, middle back 32, biceps 30, abdominals 28,
            triceps 22, lats 20, lower back 9, traps 9, calves 9,
            forearms 7, abductors 5, neck 2, adductors 1
```

### Critical — a whole pattern × equipment cell is empty

**Bodyweight vertical press: zero entries.** `EquipmentAccess.permitted(for:
.bodyweight)` restricts a bodyweight-only lifter to `equipment == .bodyweight`
exercises only, full stop. Cross-tabulating pattern × equipment for that
equipment value:

```
bodyweight pattern counts: cardio 22, hinge 10, lunge 9, horizontal press 8,
  squat 6, raise 6, carry 5, vertical pull 5, flexion 5, stretch 4,
  plyometric 4, curl 3, rotation 1, horizontal pull 1, extension 1,
  vertical press 0
```

A bodyweight-only user can never be prescribed an overhead-pressing
movement — not "rarely," literally never; plan generation has nothing to
select. This traces to the source data, not the derivation rules: the
412-slug MoveKit list itself has no `handstand-push-up`, `pike-push-up`, or
similar slug (`grep -i "handstand\|pike" movekit-exercise-slugs.txt` →
nothing). Since IDs must match the licensed animation library and the
catalog is fixed, **this cannot be fixed by editing `overrides.json` or
`derivation-rules.json`** — it requires either licensing additional MoveKit
slugs for this movement or accepting the gap and documenting it (e.g.
disabling vertical-press balancing for bodyweight-only plans rather than
silently producing lopsided ones).

Two more thin cells worth naming: **bodyweight horizontal pull has exactly
one option** (`inverted-row`) and **bodyweight curl has exactly one usable
option** (`nordic-hamstring-curl`; the other two bodyweight-curl entries are
`neck-curl` and the mistagged `bodyweight-spinal-jefferson-curl` from §1,
which isn't a curl at all) — so a bodyweight-only pulling day will repeat
the same inverted row every session with no variation.

### Important — missing movements a serious lifting app would have

Checked the source slug list directly (not just the built catalog) for
these, so their absence is a genuine gap in the licensed exercise set, not a
derivation-rule miss:

- **No ab-wheel / barbell rollout.** `grep -i "ab-wheel\|rollout"` over the
  412 slugs → nothing. One of the most common loaded core exercises in
  general strength programming is entirely absent, despite abdominals
  having 28 primary-muscle entries otherwise.
- **No barbell sumo deadlift.** The deadlift family has
  `barbell-deadlift`, `barbell-romanian-deadlift`, `barbell-stiff-leg-deadlifts`,
  `deficit-deadlift`, `snatch-grip-deadlift` — all conventional-stance. Sumo
  only exists as `kettlebell-sumo-deadlift` and
  `smith-machine-sumo-romanian-deadlift`. For an app that will presumably
  generate powerlifting-style programs, missing the barbell sumo deadlift
  entirely is a real hole.
- **No pistol squat / single-leg bodyweight squat progression.** Given the
  bodyweight-squat cell is already thin (6 entries: `bodyweight-squat`,
  `bodyweight-box-squat`, `sissy-squat`, `cossack-squat`,
  `bulgarian-split-squat` is actually a lunge, `jump-squats`), the single
  most common "bodyweight leg day got hard" progression is missing.
- **No glute-ham raise / GHD-style exercise.** Only
  `reverse-hyperextension` covers this posterior-chain-machine niche.

### Important — muscle-group imbalance

- **Adductors: 1 exercise in the entire 412-entry catalog**
  (`machine-hip-adduction`), machine-only. Abductors fare only slightly
  better at 5, all `raise` pattern. Any adductor-focused accessory work is
  structurally impossible to program except on a machine.
- **Neck: 2 exercises** (`neck-curl`, `neck-extension`) — thin but
  plausibly acceptable scope for a general lifting app; noting for
  completeness, not flagging as urgent.
- **Traps: 9 exercises, all shrug-pattern.** Face pulls and rows carry
  traps only as secondary, which is reasonable, but it means every
  trap-primary exercise is a shrug variant — no variety within the "traps"
  primary slot itself. Minor.

### Sound

Bench-press family (10 variants across barbell/dumbbell/cable/kettlebell/
smith), overhead-press family (8 variants), pull-up/chin-up family (7
variants), lunge family (12 variants), and leg-press/leg-extension/leg-curl
machine coverage are all genuinely solid — no gap worth flagging there.

## 3. Store schema

Read all nine `@Model` types in `LiftingPlan/Store/`. CloudKit-compatibility
conventions (optional/defaulted properties, no unique constraints, optional
relationships with inverses) are followed consistently and correctly
throughout — this part of the schema is sound and I have no findings against
it mechanically.

### Important — `UserProfile.bodyweight` / `BodyMetric` overlap is worse than "no sync rule"

The two fields don't just lack a sync rule — **neither has a write path in
the app at all.** `grep -rn "BodyMetric"` across `LiftingPlan/` turns up
exactly three hits: the model's own declaration, its schema registration in
`StoreContainer.swift`, and a doc-comment reference from `UserProfile`. No
view, no service, nothing ever constructs a `BodyMetric`. Likewise,
`grep -i "bodyweight"` across `Views/` and `Services/` (excluding the two
model files) finds nothing — `SettingsView` has no bodyweight field, so
`UserProfile.bodyweight` is set only via the memberwise initializer and
never mutated afterward either.

So today: not a duplication bug, but two half-built features — a
"convenience copy of the latest reading" that nothing ever refreshes, and a
"tracked history" series that nothing ever appends to. That's arguably
better than active data corruption, but it means **whoever builds the
bodyweight-entry UI next will face exactly the sync-rule question the
doc-comment already anticipates** (`UserProfile.swift:27`: "this is a
convenience copy of the latest reading for callers that don't need the
series") with no code to model it against. **Recommendation:** when that UI
lands, write bodyweight only to `BodyMetric` (the series is the source of
truth) and derive `UserProfile.bodyweight` from `BodyMetric` at read time —
or drop the `UserProfile.bodyweight` field entirely and make "latest
bodyweight" a computed property over `BodyMetric`, eliminating the
duplication instead of adding a sync rule to maintain.

### Important — `BodyMetric` has no relationship to `UserProfile`

`BodyMetric` is a bare `@Model` with `date` and `bodyweight` — no
`@Relationship` back to `UserProfile`, no inverse. With exactly one
`UserProfile` expected (enforced only by app convention, not the schema —
correctly noted in `UserProfile`'s own doc-comment, since CloudKit forbids
unique constraints), this is harmless today. But it means `BodyMetric` rows
are not actually *owned* by anything in the data model; if the app ever
needs to reason about "this user's" metrics versus stale data from a
different profile (multi-profile support, or profile reset/re-onboarding
producing a second `UserProfile` row), there is no way to disambiguate. Add
an optional `var profile: UserProfile?` with a cascade-delete inverse now,
while it's a two-line change, rather than after CloudKit records already
exist without it.

### Minor — no application-level guard against a duplicate `UserProfile`

The doc-comment says "exactly one instance is expected... enforced in
application code," but no such enforcement was found anywhere in
`LiftingPlan/` (searched for profile-creation call sites). If it exists,
it's not visible from the `Store/` or obvious `Services/` layer. Not
verified as broken, but worth the owner double-checking there's an actual
singleton-fetch-or-create path before this ships broadly, since a second
CloudKit-synced `UserProfile` row created from two devices before first sync
would silently produce ambiguous state (which one does `permits(exercise:)`
read from?).

### Sound

`TrainingPlan → TrainingWeek → WorkoutDay → PlannedExercise → LoggedSet` is
a clean, well-normalized cascade hierarchy with correct inverses throughout.
`PlannedExercise.displayName` as a denormalized copy of the catalog's
display name, with an explicit comment warning never to match on it as an
identity, is exactly the right pattern for the schema-evolution problem in
§4. `LoggedSet.load: Mass?` / `StrengthBaseline.load: Mass?` both correctly
use `nil` (not zero) for "no external weight," consistently applied.

## 4. Schema evolution readiness

**There is no versioning story at all.** Searched for `schemaVersion`,
`catalogVersion`, `VersionedSchema`, `SchemaMigrationPlan`, "migration" —
zero hits anywhere in `LiftingPlan/`. `StoreContainer.schema` is a flat,
unversioned `Schema([...])`, and nothing in the catalog JSON or the
`Exercise` model carries a catalog build version or generation date.

Walking through what actually happens when a future release changes the
catalog, given `PlannedExercise.exerciseID` / `StrengthBaseline.exerciseID`
are the only link back to the catalog:

- **An exercise ID is removed** (e.g. the owner decides a slug was wrong and
  drops it, or MoveKit deprecates an animation): existing
  `PlannedExercise`/`StrengthBaseline`/`UserProfile.avoidedExercises` rows
  keep the old `ExerciseID` forever — SwiftData/CloudKit has no foreign-key
  enforcement, so nothing breaks at the storage layer. But
  `ExerciseCatalog.exercise(id:)` returns `nil` for it going forward.
  `PlannedExercise.displayName` is denormalized specifically so history
  stays readable in this case — that part was clearly designed for this
  scenario and works. What is *not* designed for it: `mediaAsset` lookup,
  muscle-group/pattern-based analytics, and `substitutes(for:)` (used to
  suggest a replacement) all silently produce nothing for an orphaned ID,
  with no code path that detects "this logged history references a
  since-removed exercise" and prompts a remap. Right now `exercise(id:)`
  is called from exactly nowhere else in the app (confirmed via
  `grep -rn "exercise(id:"`), so this is a live risk for whoever wires up
  history/progress views next, not yet an active bug.
- **An exercise ID changes** (e.g. a slug is renamed for correctness, or an
  override changes what a stale slug means): this is worse — old logged
  sets now point at an ID that still resolves, just to different data than
  what was true when the set was logged. There is no `id`-rename table and
  no mechanism to distinguish "same ID, same exercise, corrected data" from
  "same ID, now means something else." Given §1 found real correctness
  bugs the owner will presumably want to fix in a future build (e.g. the
  `barbell-deadlift` primary-muscle fix), this is not hypothetical — fixing
  §1's findings *is* exactly this scenario. A user who logged sets against
  today's (wrong) `barbell-deadlift` primary-muscle data will have that
  history silently reinterpreted the next time the app reads catalog data,
  because nothing captures "which catalog version produced this record."
- **The catalog is regenerated with `build-catalog.py`** (e.g. a
  `derivation-rules.json` tweak reclassifies a swath of exercises, as
  happened historically per the code comments referencing prior "lat"/
  "ring"/"rope" incidents): the output is deterministic and diffable, which
  is good practice, but nothing in the app ships or checks a hash/version
  of `exercises.json` against what a `TrainingPlan` was generated with.

**Recommendation:** add a `catalogVersion: String` (or content hash) to the
generated `exercises.json` (one new top-level field, cheap to add in
`build-catalog.py`) and stamp it onto `TrainingPlan` at generation time.
That alone doesn't solve remapping, but it makes "was this plan generated
against catalog vN" answerable, which is the prerequisite for ever writing
a remap/migration path later. Given the catalog is now confirmed
permanently fixed in *membership* (§ framing note) but will still need
occasional *correction* passes per §1's findings, this is worth doing
before the first correction ships, not after.

## 5. The generator (`Tools/build-catalog.py`)

Precedence is real and mostly well-documented in comments: derivation rules
→ free-exercise-db enrichment → overrides, with overrides re-deduping
primary/secondary after the fact (line 153) — that specific re-dedup fix is
a genuinely good piece of defensive code with a clear comment explaining why
it's needed. The script is deterministic (confirmed: sorted output, sorted
keys, `sort_keys=True`) and prints a coverage report including fallthrough
lists, which is a reasonable safety net for catching *new* slugs that don't
match any rule.

### Important — the difficulty cascade's precedence isn't justified and produces a real skew

Difficulty is derived as `pattern > equipment > mechanic > default`
(lines 170–177), with only two comments explaining the *fedb-vs-derived*
part of the logic (why fedb may only raise, never lower, difficulty) — the
choice to check `equipment` **before** `mechanic` is not explained anywhere,
and it has a real, measurable effect: **69 of 412 entries (17%) are
compound movements on machine/cable/band equipment rated "beginner" purely
because the equipment check fires before the mechanic check**, including
`machine-hack-squat`, `smith-machine-squat`, `smith-machine-front-squat`,
and `reverse-hack-squat` — all heavy, technical, loaded lower-body compounds
rated the same difficulty as an isolation exercise. There is a real
argument that machine/cable equipment is more beginner-appropriate
regardless of mechanic (guided path, lower stabilization demand, lower
injury risk) — but that argument, if it's the intended rationale, should be
a comment next to `difficultyByEquipment`, not something a reader has to
reverse-engineer from precedence order. As it stands, whether "equipment
before mechanic" is a deliberate design choice or an oversight is not
determinable from the code, which is itself the problem the audit brief
asked about.

### Minor — no validation that overrides target real slugs or known fields

`entry.update(overrides[slug])` (line 149) is a raw dict merge with no
schema check. Two failure modes it doesn't guard against, neither currently
triggered (verified via script — zero dead override keys, zero unrecognized
override fields in the current `overrides.json`) but both silent if they
ever occur:
- An override key that doesn't match any slug in
  `movekit-exercise-slugs.txt` (e.g. a typo, or a slug that got removed from
  the source list) does nothing and prints nothing — the override is
  silently dead.
- An override field name that doesn't match one of `Exercise`'s
  `CodingKeys` (e.g. `"patttern"`) writes into the JSON fine, and
  `Exercise.init(from:)` in `Domain/Exercise.swift` silently ignores unknown
  keys per its own doc-comment ("unknown keys are ignored, so a catalog
  produced by a newer build still loads in an older one") — a deliberate
  forward-compatibility feature that doubles as a silent-typo trap here.
  **Fix:** have `build-catalog.py` assert every override key is a member of
  the slug list, and every override value's keys are a subset of a known
  field set, failing the build loudly if not (mirrors the existing
  duplicate-ID check at lines 197–200).

### Minor — substring-match fragility remains structural, not just historical

The longest-substring-wins matching (`longest_match`, lines 44–50) is the
root cause of every miscategorization found in §1 that traces to the
derivation rules (`spinal-jefferson-curl`, `upright-row`,
`stability-ball-leg-curl`/`towel-slide-leg-curl`). It currently produces
correct results almost everywhere only because the *current* 412-slug list
happens not to collide badly — e.g. `narrow-pulldown` contains `row` as a
sub-string of "nar**row**," and only produces the right answer because
`pulldown` (8 chars) is a longer, also-matching key that wins. There is
exactly one slug in the current list containing "narrow" — if a future
MoveKit release (or a corrected/expanded slug list, however the owner
sources one) ever adds e.g. a `narrow-grip-bench-press`, it would silently
resolve to `horizontal pull` via the same "row"-inside-"narrow" collision
this project has hit four times before, because there is no
word-boundary check anywhere in `longest_match`. Given the catalog's
membership is now fixed, this is lower urgency than it would otherwise be
(no new slugs are expected) — but if the owner ever regenerates against an
updated MoveKit export, this will bite again in the same way. **Fix:**
require key matches to fall on `-`-delimited token boundaries (split the
slug on `-` and check token/token-sequence membership, rather than raw
substring containment) — this is a small, mechanical change to
`longest_match` and would have prevented every substring-class bug found in
this audit and its predecessors.
